# Skill Registry

`family` is the user-facing grouping field (last column, single source of truth). Each skill has exactly one primary `family`; cross-cutting roles use tags in the Group Alias Map. Display names, aliases, and shared Phase A family-entry mapping live in the Group Alias Map below; host `context-routing.md` files own only the trigger and platform routing guardrails.

## Cluster Notes

- Research remains a narrow artifact-stage cluster; the current task owner selects the matching specialist directly from the requested artifact and verified upstream state.
- Design analysis and evidence capabilities stay specialized; implementation surface variants remain conditional `design-frontend` profiles until they prove a distinct owner or oracle.
- 7.0 coordination concepts remain only as lightweight support skills.
- `plan-short-term-docs` owns both the active current-horizon plan and explicit `curation`/closeout mode; curation is not a task executor or Memory mutator.
- `plan-loop-term` is a narrow Planning specialist for goal/loop completion terms; broad planning packages remain owned by `plan-long-term-package`.
- Planning family state transitions are governed by `planning_state_model.md`: discovery, requirements contracts, active plans, implementation readiness, loop overlays, package overlays, closeout, and archive admission share event/invariant rules instead of relying on natural-language confidence alone.
- Orchestration capability contracts are runtime evidence artifacts, not skills; cron, webhook, queue, automation, and event-trigger claims remain external-host-dependent until verified.
- Loop Engineering keeps readiness in `analysis-loop-readiness`, contract and verifier mapping in `plan-loop-term`, and accepted execution in `workflow-loop-runner`.
- Management family owns project Memory, Knowledge, and `project-context.yaml` location/checkpoint operations. Memory Bank stores cross-session goals, working rules, recurring mistakes, and proven practices. Knowledge Base stores accepted project domain/design/algorithm/architecture/review knowledge as current artifact-linked Markdown snapshots with typed relations, semantic revisions, and provenance observations; recurrence dimensions are derived without scores. An LLM Wiki is an optional, separately declared read-only context source selected explicitly; none of the three is an implicit fallback for another.
- Heavy artifact-producing skills require explicit artifact intent. Explicit invocation or admission of a report-family skill supplies intent for its one default Report Canvas artifact; it does not authorize target mutation or an automatic post-implementation report.
- Report Canvas is the required default presentation layer for report-family human-facing results, not a skill, router, evidence source, or new owner. One canonical source is projected into every generated `report-*` skill as local `references/report_canvas_contract.md` and `scripts/report-canvas/`, so installed skills have no sibling-plugin or undeclared plugin-root dependency. Report skills project one evidence-calibrated model into `decision`, `compare`, `trace`, or `spatial` HTML; only explicit chat-only/no-file, exact machine/canonical-format, or unavailable-artifact-surface cases use a fallback. Ordinary non-report answers stay concise chat. Visual and copy chrome follow `visual_decision_contract.md`: unchosen factory defaults are removed, and a sourced brand or the chosen Oblivion identity is kept. When the claim must be seen (3D, mesh, math surface, graphics), the inspectable-visual gate requires `spatial` with real geometry instead of restyling or a card wall.
- Design implementation and its token/decomposition/visual gates use the same visual-decision rule. Missing source or token evidence is not filled with a generative landing-page kit.
- Implementation understanding is pulled only when a concrete next decision benefits from it: `report-implementation-explainer` creates a derived navigation artifact, and `plan-behavior-discovery` re-opens the artifact's cited source/runtime anchors before turning current behavior into the next product decision. Neither forms an automatic post-implementation chain or proves the user's mental state.
- Runnable prototyping is a separate evidence-bearing execution mode: `plan-behavior-discovery` may select the question, `workflow-prototype` builds only the bounded throwaway discriminator and preserves it through decision-owner observation, and `workflow-implementation` owns any selected production change. No stage activates the next automatically, and pending prototype evidence is not cleaned up automatically.
- Agentic SDLC planning may use `plan-decision-map` before ordinary discovery when a stable target still has multi-session decision dependencies; explicit `plan-stakeholder-questionnaire` artifacts can request stakeholder answers for later discovery or a requirements brief. The ordinary flow remains `plan-requirements-discovery` to `plan-requirements-brief` to `plan-long-term-package` or `plan-short-term-docs`, and `report-lifecycle-artifacts` packages resulting lifecycle artifacts and evidence. No stage starts the next automatically.
- Invocation surface metadata lives in each skill's `agents/openai.yaml` policy. It classifies activation shape (`explicit_procedure`, `evidence_gate`, `support_only`) without replacing Routing Card roles or user authority. Intent-matched procedures may be implicitly exposed; governed persistent/external/loop/lifecycle operations remain explicit-only. Direct specialist selection never expands write or side-effect authority.
- `analyze_context_surface.py` is advisory only. It highlights likely context leakage and fanout, but does not fail release verification or penalize long explicit procedure skills by itself.
- WorkItem lifecycle is a schema-governed state model for `triage -> explore -> ready -> implement -> verify -> review -> closed`. It can link to `TaskRun` or `LoopRun`, but it is not a queue runtime, scheduler, Kanboard source of truth, or LoopRun replacement.
- Work horizon metadata lives in plan/workflow skill `agents/openai.yaml` files. `work_horizon`, `planning_altitude`, and `execution_mode` separate task/ticket state, short-plan artifacts, long-plan packages, loop overlays, plan execution, and support facets without adding runtime automation.
