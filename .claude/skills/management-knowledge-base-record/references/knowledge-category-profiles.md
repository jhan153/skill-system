# Knowledge Record Category Profiles

Read only the selected category. Every category still uses the shared envelope, overlap classification, semantic revision, relation, observation, index, and readback rules from `knowledge_record_contract.md`.

## Domain

Admit an accepted project term, invariant, state rule, or operational consequence. Require canonical code, schema, or specification refs and name direct consumers.

Record vocabulary and meaning, allowed/forbidden states, invariant, operational consequence, scope/exceptions, and consumers. Reject generic background, tentative interpretation, task status, implementation chronology, and interaction history.

## Design

Admit an accepted recurring local product or visual design rule. Require actual design/design-system and implementation refs; do not invent tokens, components, variants, or states.

Record product intent, affected surfaces and states, approved component/token/control, layout or interaction rule, accessibility constraint, implementation symbols, and validation expectation. Reject generic UI patterns, one-off taste, unaccepted concepts, and screenshot critique without an operational rule.

## Algorithm

Admit an accepted project algorithm choice or invariant. Require the problem constraints, selected method, implementation anchors, and representative verifier or benchmark conditions.

Record correctness invariants, time/space behavior, comparison conditions, and rejected or superseded alternatives with reasons. Separate measured facts from rationale. Reject unresolved selection, generic textbook explanation, transient or unrepresentative benchmark noise, and a repeated run of an existing identity.

## Architecture

Admit an accepted boundary, ownership rule, dependency direction, lifecycle, or data-flow invariant. Require direct module, schema, code, or accepted design anchors plus representative owners/consumers.

Record boundary and owner, dependency direction, lifecycle/data flow, invariants, allowed exceptions, and migration or consumer consequences. Inspect one material counterexample or exception when relevant. Reject speculative diagrams, generic patterns, task chronology, and a clean diagram that conflicts with source ownership.

## Code Review

Admit a recurring repository-specific review rule or explicit repository policy. Require detection cues, a correct pattern, exceptions, affected scope, tool support where relevant, representative source pointers, and independent provenance roots for claimed recurrence.

Record why the rule matters in this repository without copying reviewer identity or raw comments. Reject one-off bugs or comments, personal style, generic lint advice, and repetition copied from one source.

## Decision

Admit one accepted durable project decision whose identity is not better owned by the domain, design, algorithm, architecture, or code-review categories. Require the accepted decision source plus stable plan/work-item and affected canonical anchors.

Record context, accepted decision, effective scope, consequences, rejected or superseded alternatives with reasons, and implementation/consumer links. Reject tentative plan language, TODOs, estimates, execution chronology, and a decision that merely restates an existing category identity.
